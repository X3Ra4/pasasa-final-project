# Організація командної роботи

Автор репозиторію: **X3Ra4**. Імена інших студентів не надані. Цей документ задає
процес для реальної команди; він не є свідченням вигаданих зустрічей чи чужого внеску.
Фактичний склад і персональний внесок потрібно узгодити з викладачем.

## Рекомендовані напрями відповідальності

| Напрям | Результат роботи |
|---|---|
| Frontend | Адаптивні шаблони, форми, дошка, доступність, скриншоти |
| Backend / DB | Моделі, міграції, правила доступу, REST API |
| QA | Позитивні й негативні сценарії, баг-репорти, регресійні тести |
| DevOps / документація | Контейнери, CI, інструкції, демонстрація |

Одна людина може виконувати декілька ролей. Авторство комітів і pull request має відповідати
фактичному виконавцю. Додавати фіктивних співавторів чи заднім числом приписувати роботу не потрібно.

## Робочий цикл

1. Завдання створюється у GitHub Issues з критеріями приймання; для помилок є окремий шаблон.
2. Робоча гілка від `taskflow-team-project` називається `feature/<issue>-short-name` або `fix/<issue>-short-name`.
3. Виконавець додає код і перевірки, відкриває PR у `taskflow-team-project`.
4. Інший учасник переглядає код і результати тестів. CI має бути зеленим.
5. Після демонстрації критерію приймання issue закривається; документація оновлюється разом із кодом.

За Scrum команда може планувати короткі ітерації: спочатку авторизація/моделі,
потім дошка/команда, далі API/розгортання, наостанок тестування й захист.
Планування, короткі щоденні обговорення, review і retrospective проводять реально,
а домовленості записують у задачах. Scrum у вихідному завданні рекомендований.

## Definition of Done

- Критерій приймання відтворюється через сайт або API.
- Є перевірка негативного сценарію, особливо прав доступу.
- Повний набір тестів проходить на PostgreSQL.
- Міграції включені, секрети не потрапили в Git.
- Інструкція й API-документація відповідають поточному коду.

Завдання, дефекти та результати поточної реалізації — у [TRACKER.md](TRACKER.md).
